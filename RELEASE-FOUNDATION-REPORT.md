## 2. Правила денег и провайдер РФ

Выполнено:

- Подготовлен [RELEASE-RF-RULES.md](RELEASE-RF-RULES.md): подтверждённые решения отдельно от предложений, жизненный цикл пополнения/штрафа/возврата, ошибки и гонки, требования к журналу и условия открытия реальных платежей.
- Сверены официальные документы ЮKassa по возвратам/уведомлениям/API; ссылки внутри задания.
- Прочитан открытый пользователем существующий кабинет: API-подключение и только `payment.succeeded` на адрес прежнего сервиса. Секреты не открывались/не копировались. Старый магазин не изменён и не удалён.
- Закрыт незавершённый платёжный адаптер: hosted-среда не запускается в manual и с неизвестным/неготовым live-провайдером; disabled отвечает 503 на пополнение и webhook. Локальная симуляция сохранена.

Не выполнено:

- Новый договор/магазин Disbit и согласование именно остатка с удержаниями и возвратами. Старый магазин — технический пример, не подтверждение допуска нового бизнеса.
- Финальное подтверждение владельцем предложенных RUB/возврата/лимитов/возраста и юридического лица. Кабинет доступен, но реквизиты и действующий договор на Disbit не утверждены.
- Юридическая квалификация, чеки, оферта, новая политика обработки данных, одобрение магазинов приложений. Документы с выдуманными реквизитами не опубликованы.
- Настоящие пополнения/возвраты/сверка и серверный расчёт штрафов — следующий денежный этап. Деньги и биты клиентов не изменялись этим заданием.
- Удаление старого магазина: отложено до готовности новой системы и отдельной проверки незавершённых платежей/возвратов.

## 3. Основа эксплуатации

Выполнено в коде/шаблонах:

- Проверка окружения до открытия БД: явные абсолютные пути, HTTPS origin, release SHA, длинный admin key, отделение staging от disbit.ru.
- При обычном hosted-запуске отсутствующая база/папка медиа вызывает ошибку вместо молчаливого создания пустых аккаунтов. Первичная инициализация требует отдельного явного флага.
- Health содержит среду, SHA и возможности API; readiness проверяет БД. Ответы не кешируются. Добавлены graceful shutdown, busy_timeout, скрыт Express-заголовок.
- Миграции не проглатывают произвольные ошибки; уже существующие колонки определяются по схеме. Повторное обновление старой искусственной БД сохраняет отметки.
- Offline backup/restore: SQLite вместе с медиа, WAL, проверка integrity/foreign keys, файловых ссылок, числа строк и SHA-256; отказ от перезаписи и symlink. Восстановление выполняется только в новый каталог.
- Отдельные env-шаблоны, пользователи systemd, ограниченные права, Caddy staging со списком разрешённых IP/noindex, инструкция deploy/rollback, шаблон ежедневного backup timer. Basic Auth заменён при ревью, поскольку он конфликтует с Bearer-заголовком приложения.
- Docker: npm ci, непривилегированный процесс, исключены секреты/БД/медиа/архивы из контекста. Добавлены правила Git для новых секретов и runtime-данных.
- Подготовлен GitHub Actions workflow на Node 22/24; без автоматического deploy.
- Почта: hosted больше не выдаёт код в лог при отсутствии провайдера; resend возвращает фактическое `sent`. Настоящая доставка пока не настроена.

Не установлено/не подтверждено вне локальной машины:

- DNS/HTTPS staging, Linux-пользователи, systemd, timer, env, обновление production и его миграция — нужен SSH.
- Внешнее зашифрованное резервное хранилище, канал оповещений, автоматическая ротация копий. Копия на том же сервере не заменяет внешнюю.
- Восстановление настоящих production-данных, измерение RPO/RTO. Тест выполнен на искусственной БД и файле, а не на персональных данных пользователей.
- Реальная почта, домен отправителя и получение письма.
- Docker-образ запущен локально и в GitHub Actions на искусственных данных; production-контейнер не развёрнут.
- Проверка истории Git на старые чувствительные архивы и согласованная очистка. Уже отслеживаемые изменения server-backups оставлены как были.
- Старые APK защищены серверными правилами от обхода пруфа/прошлых дней, но полноценная функциональная совместимость старого клиента не обеспечена. Нужна политика обновления клиента.

## Следующие действия для закрытия пунктов

1. Восстановить SSH существующего сервера, сверить данные/службы и сделать проверенный снимок.
2. Развернуть закрытый staging по ops/README.md, настроить почту, проверить сценарии по HTTPS.
3. Принять денежные условия и получить одобрение сценария у провайдера; создать отдельную конфигурацию Disbit.
4. Совместно обновить backend/frontend production, проверить SHA и тестовый аккаунт после перезапуска.
5. Проверить установленный APK на физическом телефоне: камера, пруф, фон, плохая сеть, покупки за биты. Контейнер iOS собран для симулятора, остаются подпись и проверки на iPhone.
6. Настроить внешние копии/уведомления и выполнить восстановление в закрытой среде. После этого пункты 1–3 можно принимать, а деньги реализовывать по согласованному контракту.
