## Выполнено и проверено

- GET /api/blocking/plan требует сессию и возвращает расчёт только своего аккаунта.
- Интервал рассчитан по часовому поясу аккаунта; максимум 24 часа, включая переходы DST.
- Каждое невыполненное обещание имеет отдельный habitId и причину missed_promise.
- Выполнение одного обещания исключает только его; общий пропуск дня исключает все.
- API намеренно возвращает enabled:false, mode:preview, windows:[]; расчёт находится в preview. Это не работающая автоматическая блокировка.
- Добавлены явные исключения обработчиков экстренных вызовов, соответствующая видимость пакетов в manifest и инструментальные тесты исключений.
- Согласие на раскрытие Accessibility версии 1 сохраняется только после положительного нажатия. Без него ручное ограничение не активируется, даже если разрешение включили непосредственно в Android.
- Уточнены подсказки Samsung/Xiaomi. Статус различает разрешение и подключённую службу.
- Исправлено игнорирование события собственного Activity при открытом блокирующем окне. Проверено компиляцией; поведение требует телефона.
- 70 Node-тестов прошли (включая 8 тестов политики/плана/API): test-results/phase31-node.log.
- JVM: BlockingWindowTest — 2 теста, 0 ошибок.
- Debug APK и APK инструментальных тестов собираются. Журнал: test-results/android-phase31-build.log.
- git diff --check: ошибок whitespace нет.

## Не завершено в коде

Отсутствие телефона блокирует приёмку, но не объясняет эти незавершённые разработки:

1. Регистрация устройства, привязка аккаунта и версия согласия на сервере; отзыв при выходе/смене аккаунта.
2. Получение и применение серверного плана Android-клиентом. Сейчас native работает только с ручным общим интервалом.
3. Хранение отдельных окон/выбранных пакетов по habitId и синхронизация после выполнения/общего пропуска.
4. Фоновое обновление плана, поведение без сети, восстановление серверного плана после перезагрузки. Существующее переподключение Accessibility восстанавливает только ручной интервал, не получает новые серверные окна.
5. Сквозной сценарий создания обещания с нативным ограничением. Запрет создания lock-обещаний в рабочем API не снят.

До этих работ нельзя представлять API preview или собранный APK как завершённую функцию.

## Google Play — подготовка, не поданная декларация

Источник: https://support.google.com/googleplay/android-developer/answer/10964491
Дополнительно: https://support.google.com/googleplay/android-developer/answer/11150561

isAccessibilityTool=false уже указан в ресурсе службы. Нужны декларация использования API, заметное отдельное раскрытие и явное согласие. Доступ можно отозвать; мешать отключению/удалению нельзя.

Проект описания текущего прототипа для декларации:
«Disbit использует AccessibilityService для добровольного ограничения выбранных пользователем приложений. Служба обрабатывает события смены окна и идентификатор пакета, чтобы показать экран ограничения. Содержимое окон, введённый текст, скриншоты и жесты не собираются. Системные приложения и Disbit исключены. Пользователь может снять ограничение и отозвать доступ в системных настройках».

Описывать автоматические ограничения за обещания в декларации можно только после их реализации и проверки. Перед отправкой сверить текст с окончательной сборкой.

Сценарий видео: запуск → раскрытие → отмена → повторное раскрытие и согласие → системное включение → выбор приложения → ограничение → безопасный возврат в Disbit → снятие → отзыв разрешения. После интеграции добавить выполнение обещания и снятие конкретного окна.
Видео не снято: реальное поведение без устройства не воспроизводилось. Декларация не подана.

Решение при отказе: сначала изучить конкретную причину и исправить/обжаловать. Если применение API не разрешено — магазинная сборка без Accessibility-блокировщика с честным отключением функции. Usage Access + overlay НЕ считать готовой или одобренной заменой: отдельные разрешения, раскрытие, прототип и проверка правил обязательны; скрытая замена для обхода модерации исключена. Такой fallback не реализован.

## RuStore — правила проверены, одобрения нет

Источник: https://www.rustore.ru/help/developers/publishing-and-verifying-apps/app-publication/new-version-app/declare-app-permissions/permission-types

RuStore требует декларации разрешений категорий Dangerous, Special и Signature. BIND_ACCESSIBILITY_SERVICE указан как чувствительный и должен защищать службу от привязки посторонних приложений. В manifest Disbit он стоит на service; это не гарантия прохождения модерации. Подготовить описание назначения и сверить фактические разрешения итоговой сборки в консоли. Декларация и заявка не отправлялись.
