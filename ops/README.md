# Подготовка и выпуск Disbit на Timeweb

25 октября 2026. Шаблоны проверены локально, в Docker и CI; серверные службы, DNS staging и таймер ещё НЕ установлены. Консоль Timeweb доступна под root, но SSH на 188.225.34.65 пока отклоняет доступный ключ. Не переустанавливать ОС ради доступа: там пользовательская база и медиа.

## 1. Окружения

| Среда | Домен/порт | Данные | Платежи |
|---|---|---|---|
| development | localhost:3000 | существующая локальная backend/db | симуляция |
| test | 3337/3439 и временные каталоги | только искусственные пользователи | симуляция |
| staging | staging.disbit.ru → 3100 | /var/lib/disbit-staging | disabled |
| production | disbit.ru → 3000 | /var/lib/disbit-production | disabled до денежного этапа |

Отдельные Linux-пользователи `disbit-staging` и `disbit-production`, каталоги данных 0700; приложение не должно менять собственный код. Staging закрывается списком разрешённых IP в Caddy и noindex, включая API. Basic Auth не используется: он конфликтует с Authorization: Bearer приложения. Не копировать туда реальную базу/медиа для обычных тестов. Пользователь и пароль localhost не возникают автоматически на сервере.

## 2. Подготовка сервера после восстановления SSH

1. Через панель Timeweb вернуть правильный SSH-ключ существующему серверу, проверить fingerprint. Не отключать проверку сервера.
2. Проверить текущий способ запуска, рабочий каталог, Node, Caddy, фактические DB_PATH/PROOFS_DIR, свободный диск, права и сохранность бэкапов. Не печатать секреты из окружения в чат/логи.
3. Установить поддерживаемый Node 22.13+; локальная проверка сделана на Node 24.15. В CI предусмотрены 22 и 24.
4. Создать два системных пользователя, отдельные каталоги кода, данных и `/etc/disbit`; скопировать env.example в закрытые конфигурации 0600. Заполнить реальный SHA, URL и случайный ADMIN_KEY не короче 32 символов. В примерах SHA-заглушка, она не является версией релиза.
5. Скопировать текущие production-данные в новую структуру только в окне остановки после проверенного бэкапа. Сверить числа записей и файлы. Старую копию сохранить до приёмки.
6. Установить `disbit@.service` в `/etc/systemd/system/`. При иной установке Node исправить ExecStart. Дать соответствующему пользователю права только на его каталог данных.
7. Создать DNS A для staging. Задать `STAGING_ALLOWED_CIDRS` в окружении Caddy: конкретные внешние IP/CIDR тестировщиков, разделённые пробелами (не 0.0.0.0/0). При изменении IP обновлять список. Объединить Caddyfile.example с действующей конфигурацией, выполнить `caddy validate`, затем reload. Проверить 403 с постороннего IP и успешный Bearer API с разрешённого. Не перезаписывать рабочие настройки вслепую.
8. Для первого запуска совершенно новой пустой среды временно задать `INITIALIZE_DATABASE=1`; после создания базы убрать. При обычных запусках отсутствие базы или каталога пруфов останавливает сервер, чтобы потерянный mount не выглядел как пустые аккаунты. Запустить staging. Проверить `/api/health`, `/api/ready`, release SHA, регистрацию/вход, выполнение, пруф, друзей, перезагрузку. Для камеры использовать HTTPS.

## 3. Выпуск конкретной версии

1. Сохранить SHA текущей версии и проверенный бэкап. Прогнать `npm ci --prefix backend`, `npm test`, `node scripts/check-release.mjs` для выбранного коммита.
2. Разместить код отдельно: `/opt/disbit/production/releases/<SHA>`; установить зависимости `npm ci --omit=dev --prefix backend`. Runtime-данные не держать внутри checkout.
3. После staging остановить production в объявленное окно. Запустить offline-бэкап по разделу 4.
4. Переключить `/opt/disbit/production/current` на новый каталог, изменить RELEASE_SHA в закрытом env, запустить службу. Проверка конфига должна завершиться до открытия/изменения БД.
5. Проверить localhost readiness и внешний HTTPS; сравнить SHA и файлы, зайти тестовым аккаунтом, проверить сохранение после перезапуска службы. Не проводить платежи реальными деньгами.
6. Обновлять фронтенд и бэкенд вместе: новая версия требует пруф и запрещает прошлые дни. Старый APK не умеет весь новый сценарий и не считается совместимым только потому, что API отвечает. Старые запросы не обходят проверки, но UX старого клиента не гарантирован.
7. Распространять APK 1.0.3 только после обновления серверной части и полного теста телефона. APK установилась поверх 1.0.1 на Galaxy A22, но production API ещё старый; это кандидат для QA, не принятый магазином релиз.
8. При отказе остановить службу. Если схема совместима, вернуть прежний код; если нет — восстановить проверенную копию в НОВЫЙ каталог, сверить данные и переключить пути. Восстановление снимка теряет новые операции после него, поэтому нельзя делать автоматический rollback БД при работающих пользователях.

## 4. Бэкап и восстановление

База и медиа должны соответствовать одному моменту. Скрипт требует остановки приложения: `--offline` — подтверждение оператора, не автоматическая проверка отсутствия всех сторонних писателей. `VACUUM INTO` учитывает WAL; простое копирование открытого .db недостаточно. Скрипт проверяет SQLite, внешние ключи, ссылки на медиа, число строк и SHA-256 всех файлов.

```sh
systemctl stop disbit@production
node scripts/backup.mjs create /var/lib/disbit-production/disbit.db /var/lib/disbit-production/proofs /var/backups/disbit-production/NEW_TIMESTAMP --offline
systemctl start disbit@production
node scripts/backup.mjs verify /var/backups/disbit-production/NEW_TIMESTAMP
node scripts/backup.mjs restore /var/backups/disbit-production/NEW_TIMESTAMP /var/lib/disbit-restore-NEW_TIMESTAMP
```

Родитель целевого каталога должен существовать; сам целевой каталог должен быть новым. Скрипт не удаляет и не перезаписывает рабочие данные. Повреждённые копии и symlink внутри набора отклоняются. Manifest обеспечивает обнаружение повреждения, но не шифрование/защиту от злоумышленника, способного переписать весь набор.

Для ежедневного запуска установлены в проекте `backup.sh`, `disbit-backup@.service`, `disbit-backup@.timer`. После установки файлов на сервер: daemon-reload, пробный запуск службы, затем enable --now таймера. Время 03:30 UTC, есть короткая остановка приложения. Скрипт возвращает службу в работу и при ошибке бэкапа; контролировать код завершения и журнал.

Предлагаемые цели до релиза: RPO ≤24 часа, RTO ≤60 минут; это целевые значения, пока не измеренные на production. Ежедневная локальная копия не защищает от потери сервера. Нужен отдельный закрытый зашифрованный storage в согласованном регионе, доставка туда копии и проверка восстановления с него. Аккаунта/storage для этого ещё нет. Контроль свободного места и оповещения обязательны; автоматическое удаление старых копий намеренно не установлено до согласования срока хранения (предложение: 7 дневных + 4 недельных).

## 5. Эксплуатация и приёмка

- `/api/health`: процесс/версия/возможности; `/api/ready`: чтение БД. Это не подтверждение доставки писем или готовности денег.
- Проверять внешнюю доступность, ошибки службы, свободное место, возраст последней успешной копии, результат восстановления. Канал уведомлений владельца пока не выбран.
- `.env`, keystore, базы, медиа, бэкапы исключены из новых Git/Docker включений. Уже отслеживаемые архивы остались нетронутыми; историю репозитория нужно отдельно проверить на реальные данные и при необходимости согласовать очистку/ротацию.
- Production/staging не могут незаметно перейти на manual. Неизвестный/живой незавершённый провайдер останавливает запуск. Пополнение и webhook закрыты, история кошелька остаётся читаемой.
- Отсутствие почтовых ключей в размещённой среде больше не печатает код в лог вместо отправки. Настройка провайдера и реальное письмо ещё нужны.
- Миграции больше не скрывают произвольные ошибки. Тест проверяет повторный запуск схемы без потери старых отметок; это не проверка текущей production-базы.
- Dockerfile подготовлен с `npm ci` и непривилегированным пользователем. Том должен быть доступен UID node, APP_ENV/DB_PATH/PROOFS_DIR/ADMIN_KEY/RELEASE_SHA обязательны. Локальный и облачный Docker smoke проверили непривилегированный процесс, readiness и сохранность синтетической БД после замены контейнера.
- GitHub workflow только тестирует и ничего не публикует. Прогон `40134517674` прошёл на Node 22/24, Docker и macOS iOS simulator.
