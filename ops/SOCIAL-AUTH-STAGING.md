Это план настройки, не подключённая интеграция. Активное членство Apple Developer, Team ID, Services ID и ключ .p8 владельцем ещё не предоставлены. Проверено по документации Apple 5 ноября: веб-вход требует Services ID, связанный с primary App ID с включённым Sign in with Apple; источник писем нужно зарегистрировать для Private Email Relay. Самостоятельно платное членство не оформлялось.

1. Проверить возможность участия владельца в Apple Developer и завершить регистрацию.
2. Сверить Bundle ID установленного iOS-приложения с io.disbit.app из capacitor.config.json. Включить Sign in with Apple у соответствующего primary App ID.
3. Зарегистрировать отдельный Services ID для staging, связать с primary App ID. Предлагаемый идентификатор io.disbit.app.staging.web требует проверки доступности в Apple.
4. Зарегистрировать домен staging.disbit.ru и точный Return URL https://staging.disbit.ru/api/auth/oauth/apple/callback после подготовки HTTPS и обработчика POST form_post.
5. Подготовить ключ Sign in with Apple. Сохранить .p8 с ограниченными правами на сервере, записать Team ID и Key ID. Организовать обновление client-secret JWT до истечения срока.
6. При использовании скрытой почты настроить отправителя Timeweb в Apple Private Email Relay и проверить доставку.

## Требования к реализации

- Authorization Code flow. Одноразовые state и nonce, короткий срок жизни, привязка к браузеру и цели операции login/link. Для Google использовать PKCE S256. Отдельно проверить поддерживаемые Apple параметры.
- Проверять подпись токена по ключам провайдера, issuer, audience, срок действия и nonce. Идентификатор аккаунта — пара provider/subject.
- Для входа Apple обработать POST form_post и ограничения SameSite. При несовпадении state или отсутствующей привязке к инициировавшему браузеру завершать запрос ошибкой.
- Привязку запускать из действующего аккаунта после повторного подтверждения владения. На callback повторно проверить существование и действительность исходной сессии, чтобы выход или смена пароля отменяли незавершённую привязку.
- Совпадение email само по себе не связывает аккаунты. Для существующего адреса предложить войти прежним способом и явно привязать провайдера.
- Добавить уникальность provider/subject в БД, транзакции создания/привязки и обработку повторных конкурентных запросов.
- При повторном входе возвращать тот же user_id и данные. Apple может не вернуть имя повторно, скрытая почта не должна создавать дубликаты.
- Не передавать постоянный Bearer-токен через URL. Секреты, коды провайдера и токены исключить из журналов приложения и access log Caddy для callback.
- В Capacitor открывать вход через подходящий системный механизм авторизации. Возврат в Android/iOS и привязку к инициировавшему устройству проверить отдельно.

## Приёмка каждого провайдера

1. Первый вход создаёт один аккаунт, повторный возвращает его же.
2. Привязка из парольного аккаунта сохраняет user_id, привычки, друзей и баланс. После выхода вход провайдером открывает тот же профиль.
3. Совпадающая почта без подтверждения владения не открывает существующий аккаунт.
4. Чужая уже привязанная identity, подменённые state/nonce/audience/issuer, истёкший токен и повторный callback отвергаются.
5. Выход или смена пароля до callback отменяет привязку.
6. Отмена у провайдера и сетевые ошибки возвращают понятное состояние с возможностью повторить вход.
7. Проверить конкурентные callback и перезапуск сервера между началом и завершением операции.
8. Проверить браузер, Android и iOS раздельно. Записывать фактические результаты и использованный commit. Автоматические тесты с подставным провайдером учитывать отдельно от реального входа.
