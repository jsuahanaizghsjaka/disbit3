# Автоблокировка Android — серверная часть, 17 ноября 2026

Статус: сервер готов и покрыт тестами, **в рабочих средах выключен**. Нативный клиент Android план пока не получает и не применяет. Не опубликовано.

## Что сделано

- Регистрация телефона за аккаунтом с версией согласия на раскрытие доступа.
- Выдача плана ограничений по каждому обещанию отдельно: окно, причина, список приложений.
- Подтверждения телефона о применении и снятии плана (последние 200 на устройство).
- Создание обещания с блокировкой разрешено только при включённом переключателе, подключённом телефоне и хотя бы одном допустимом приложении.
- Удаление аккаунта удаляет устройства и подтверждения; экспорт данных включает список устройств.

## Переключатель

`BLOCKING_ENFORCEMENT=1` в окружении сервера. Без него поведение прежнее: `/api/blocking/plan` отдаёт `enabled:false, mode:"preview"`, обещания с блокировкой отклоняются (422, `blocking_disabled`). Регистрация телефона работает и без переключателя, ответ содержит `enforcement:false`.

Старые обещания с режимом блокировки начнут давать окна, как только переключатель включён и у аккаунта есть подключённый телефон. Перед включением проверить такие записи в базе.

## API

Все маршруты требуют сессию и отвечают `Cache-Control: no-store`.

| Запрос | Назначение |
|---|---|
| `POST /api/blocking/devices` | Тело: `platform:"android"`, `installationId` (16–64 символа `A-Za-z0-9_-`, случайный, создаётся на телефоне), `consentVersion` (сейчас 1), необязательные `label`, `appVersion`. 201 для нового, 200 для повторного. 409 `consent_outdated` с `requiredConsentVersion`, 409 `device_limit` (не больше 5), 422 `platform_unsupported`. |
| `GET /api/blocking/devices` | Свои устройства, текущая версия согласия, состояние переключателя. |
| `DELETE /api/blocking/devices/:id` | Отключить своё устройство. Чужое — 404. |
| `GET /api/blocking/plan?deviceId=…` | План. Идентификатор можно передать заголовком `X-Disbit-Device`. |
| `POST /api/blocking/devices/:id/receipts` | Тело: `planVersion`, `state` (`applied`, `cleared`, `failed`, `service_off`), необязательный `habitIds`. |
| `GET /api/blocking/devices/:id/receipts` | Последние 50 подтверждений своего устройства. |

### Ответ плана при действующей регистрации

`enabled:true`, `mode:"enforced"`, `active`, `today`, `timeZone`, `serverNow`, `windows[]` (`habitId`, `name`, `startsAt`, `endsAt`, `reason:"missed_promise"`, `apps[]`), `apps[]` (объединение), `unenforceable[]` (обещания без допустимых приложений), `planVersion`, `validUntil`, `refreshAfter`.

Во всех остальных случаях `enabled:false`, `windows:[]` и поле `enrollment` с причиной: `disabled`, `enrollment_required`, `session_changed`, `consent_outdated`. Клиент при любом таком ответе обязан снять ограничение.

## Правила, заложенные в сервер

1. Телефон действителен, пока жива сессия, из которой он зарегистрирован. Выход, сброс пароля и истечение сессии снимают регистрацию. Идентификатор устройства сам по себе доступа не даёт.
2. Регистрация того же телефона под другим аккаунтом снимает регистрацию предыдущего владельца.
3. Окно не длиннее суток аккаунта; `validUntil` не позже конца окна и не позже чем через 2 часа от ответа. Телефон без связи с сервером обязан снять ограничение в `validUntil`. Это решение в пользу человека: несправедливая блокировка хуже пропущенной. Срок задан константой `PLAN_LEASE_MS` и требует подтверждения владельца продукта.
4. Никогда не ограничиваются: сам Disbit, настройки, телефон и экстренные вызовы, системный интерфейс, клавиатуры Google и Samsung, стандартные лаунчеры, установщик пакетов. Нативный код должен сохранять собственный список исключений: серверный список не полон для всех производителей.
5. Выполнение одного обещания убирает только его окно; общий пропуск дня убирает все.

## Что должен сделать нативный клиент (не сделано)

1. Создать и хранить `installationId`, после согласия вызвать регистрацию; при смене аккаунта и выходе вызвать удаление и очистить локальное расписание.
2. Запрашивать план при запуске, после отметки обещания и по `refreshAfter` фоновой задачей; применять `windows` по `habitId`.
3. Снимать ограничение в `validUntil`, при `enabled:false` и при ошибке разбора ответа. Часы телефона сверять с `serverNow`.
4. После перезагрузки восстанавливать только план, срок которого не истёк.
5. Отправлять подтверждения `applied`, `cleared`, `failed`, `service_off`.
6. Экран создания обещания с блокировкой: выбор приложений, обработка `device_required` и `apps_required`.
