# 001 — Убрать повторное создание форматтеров дат

- **Статус:** TODO — реализация этим документом не выполнялась.
- **База:** `e9d98b5`, 28 октября 2026.
- **Приоритет:** HIGH. Категория: производительность главного потока.
- **Объём:** `frontend/script.js`, при необходимости `frontend/path-insights.js`; небольшой шаг перед переработкой рендера.

## Проблема и доказательство

`frontend/script.js:4816–4819`:

```js
function formatDay(key) {
  return keyToDate(key).toLocaleDateString('ru-RU',
    { weekday: 'short', day: 'numeric', month: 'long' });
}
```

`render()` вызывает календарь и статистику даже при активном Today. Тепловая карта вызывает `formatDay()` для каждой из 112 ячеек (`script.js:2331`), её текстовая версия — ещё раз для прошлых дней (`path-insights.js:58–63`). В синтетическом прогоне на текущем коде получено **259 вызовов formatDay на один render**.

Измерение в Chromium 156: 259 вызовов текущего `formatDay` — 36,0 / 38,3 / 44,9 мс; повторное использование одного `Intl.DateTimeFormat` — 0,9 / 0,9 / 0,8 мс. Все 259 строк совпали. Исходные результаты: `plans/date-format-results.json`, воспроизведение: `plans/date-format-audit.js`. Это микротест на ПК; он не предсказывает общий коэффициент ускорения приложения.

## Цель

Создать форматтер один раз для каждого реально используемого набора locale/options. Сохранить `keyToDate()`, порядок частей даты, локальный часовой пояс и все текущие русские подписи:

```js
const dayLabelFormatter = new Intl.DateTimeFormat('ru-RU', {
  weekday: 'short', day: 'numeric', month: 'long'
});
function formatDay(key) {
  return dayLabelFormatter.format(keyToDate(key));
}
```

Константу разместить до первого вызова `formatDay` во время `init`, с учётом порядка глобальных объявлений. Не создавать новый `Intl.DateTimeFormat` внутри циклов. Не менять формат ключа календарного дня и правила учёта часового пояса.

## Подшаги

1. Внести минимальную замену в `script.js`, отдельно сравнить 259 выходных строк с базой.
2. Проверить `operationDate()` в `path-insights.js:100–105`: для его полного формата дата/время завести отдельный переиспользуемый форматтер, если измерение списка показывает заметную стоимость. Он не должен использовать формат без времени.
3. Для `apiCall` / `apiCallStrict` (`script.js:340,359`) получить строку системного часового пояса один раз на запуск/возврат приложения, а не конструировать форматтер в каждом запросе. Не заменять часовой пояс на UTC или принудительную Москву.
4. Повторить микротест с теми же 259 датами, без CPU throttle и с одинаковой версией браузера.
5. Повторить общий render-бенчмарк; отчёт должен отделять выигрыш форматирования от оставшихся пересчётов статистики.
6. Кэш самих строк добавлять только при оставшейся измеренной необходимости. Если нужен — ограничить 512 ключами, включить locale/timezone в ключ и сбрасывать при смене этих параметров. Для этого шага он не обязателен.

## Границы

- Не переписывать календарь, деньги, расписания или `keyToDate` в этом изменении.
- Не заменять Intl ручной сборкой названий месяцев.
- Не менять шрифты и русскую типографику ради результата микротеста.
- Не обещать, что весь Disbit станет в 40 раз быстрее: оптимизируется конкретная горячая операция.

## Проверка и критерий завершения

- `node --check frontend/script.js`; `node --check frontend/path-insights.js`, если менялся.
- Сравнить подписи на переходе декабря/января, 29 февраля, понедельника/воскресенья и в двух системных часовых поясах.
- Визуально проверить Today, календарь, тепловую карту, журнал и детали операции.

- На A22 проверить, что смена даты после возврата приложения обновляет «Сегодня» и подпись даты.
- Готово, когда выходные строки и дневная семантика сохранены, а создание форматтеров отсутствует в горячих циклах.
