## Проблема

### Карточки сохраняются внутри экрана, но уничтожаются между экранами

В `frontend/script.js:1458–1495` уже есть полезный кэш разметки по цели, сцене и экипировке. Полной пересборки SVG на каждый вызов нет. Однако при переходе на экран Marathon список `routes` сужается до выбранного маршрута, а остальные узлы удаляются:

При возвращении Today удалённые маршруты создаются заново; `frontend/script.js:1494` снова разбирает SVG через `innerHTML`. При нескольких маршрутах это работа прямо в обработчике перехода.

Ещё один расход, который устраняется планом 002: в `renderWalkerCard` на `frontend/script.js:1483`, `:1484`, `:1532` трижды вызывается расчёт, проходящий историю. `stepsDone()` на `:1052–1061` строит `Set` ключей дней. Контракт для этого плана: получать `{ goalId, done, total, percent, streak, finished, revision }` один раз для ревизии истории, а не вычислять поля при каждом обращении к DOM.

## Целевой результат

1. Возврат на уже открытый маршрут/студию не пересоздаёт неизменённые SVG и не запускает шаг повторно.
2. Сцена обновляет текст, `scaleX(percent / 100)` и положение существующего персонажа. Идентификатор градиента остаётся уникальным для смонтированного экземпляра, стабильным при изменении порядка карточек.
3. Подробный персонаж, шесть сцен, экипировка, покупки и полномочия сервера сохраняют текущие правила. Снимок завершения остаётся отдельным кратким наградным движением; 700 мс не сокращать автоматически ради числа.
4. Предлагаемый профиль камеры для согласования качества пруфа: `width: { ideal: 1280, max: 1920 }`, `height: { ideal: 720, max: 1080 }`, `frameRate: { ideal: 24, max: 30 }`; при отказе ограничений — fallback 640×480/24 FPS, затем понятная ошибка. `facingMode` сохраняется. Эти значения вводить после проверки читаемости реальных тестовых пруфов; не подменять качество одним ограничением размера.
5. Зеркальное превью и сохранённый результат совпадают. Для записи через canvas обрабатывать новые видео-кадры через `requestVideoFrameCallback` при поддержке; fallback ограничивает рисование 30 FPS. Не выполнять два canvas draw для одного кадра источника.
6. После закрытия камеры, предпросмотра или ухода в фон нет живых camera/microphone/canvas tracks и повторяющегося цикла рисования. Готовый Blob сохраняется до отправки, пересъёмки или явного отказа пользователя.
7. Лимиты продукта остаются: видео до 15 секунд; отправка до 25 МБ; загрузка только живого пруфа; подтверждение выполнения и денежные последствия определяет сервер.

## Соглашения проекта

- Сохранять кэширование сцены из `frontend/script.js:1486–1497`; расширить срок жизни узла, а не заменить его глобальной пересборкой.
- Позицию персонажа и прогресс изменять через `transform`, как на `frontend/script.js:1517`, `:1532`. Группы конечностей и их `transform-origin` находятся в `frontend/path-journey.css`.
- `ensureWalkerObserver()` на `frontend/script.js:1558–1567` уже ограничивает активность видимыми карточками. Сохранить это поведение и корректно `unobserve` только при окончательном удалении/эвикции.
- `frontend/path-journey.css:19` намеренно отключает постоянные анимации среды. Не возвращать декоративные infinite-анимации в фон ради «живости».
- Имеющаяся защита `proofCameraRequest` от завершения устаревшего запроса (`frontend/script.js:4019`) обязательна и для нового жизненного цикла.

## Подшаги реализации

### A. Сцены и студия

1. После плана 002 передавать в `renderWalkerCard` готовый view model. Временно, если план 002 ещё не применён, считать `stepsDone(g)` ровно один раз в начале функции и вычислять `percent/finished` из полученного `done`; такой переходный код не должен стать вторым постоянным кэшем.
2. Ввести владельца scene instance с ключом `goal.id` и сигнатурой `{sceneId, equipmentId, artworkVersion}`. Для переходов Today↔Marathon отделить «сейчас не показывается» от «маршрут удалён». Выбор другого маршрута не уничтожает карточки всех остальных целей.
3. Заменить индексную часть gradient ID стабильным ID экземпляра. Перестановка маршрутов не должна делать SVG устаревшим только из-за нового индекса.
4. Для большого списка целей выполнить отдельный trace. Если создание невидимых сцен занимает более 50 мс одним заданием, монтировать подробную сцену при приближении к viewport, оставляя placeholder фиксированного размера. Не добавлять анимацию при появлении каждой карточки.
5. В `renderAvatar()` разделить `ensureAvatarShopMounted()` и `updateAvatarShopState()`. Первый создаёт неизменяемые шаблоны один раз; второй меняет `aria-pressed`, selected/locked, текст цены и баланс. Изменение темы/экипировки должно инвалидировать только зависимые превью.
6. Собирать пачку новых вариантов через `DocumentFragment`/одну вставку; не очищать весь магазин при выборе одного предмета. Кэш строк artwork допустим по ограниченному ключу экипировки; не кэшировать вечно пользовательские seed/фотографии.

### B. Камера, запись и предпросмотр

7. Снять baseline отдельно для raw-stream и зеркального canvas на A22: разрешение/FPS `track.getSettings()`, выбранный MIME, число draw, размер 15-секундного файла, long tasks, PSS/JS heap. В кадре использовать нейтральную тестовую сцену; не снимать человека и не отправлять реальный материал автоматикой.
8. Ввести явное состояние медиа: исходный stream, производный record stream, recorder, rAF/video-frame callback ID, timer, chunks, preview URL. Один `disposeCapture()` останавливает все принадлежащие сессии tracks, recorder и callback, отвязывает `cam.srcObject`, очищает chunks после сборки Blob. Функция должна быть безопасна при повторном вызове и при отказе разрешения.
9. На `proofShowPreview` остановить захват и цикл копирования, сохранив готовый Blob. `proofRetake` сначала очищает прежнее preview, затем заново вызывает `startProofCam`; не показывать чёрный video как будто камера уже работает.
10. На закрытии preview вызвать `pause()` для видео, очистить `src`, выполнить `load()` при необходимости, очистить `img.src`, отозвать object URL. При ошибке отправки готовый Blob сохраняется для повторной попытки; очищать его при окончательном выходе.
11. Подключить `visibilitychange`, `pagehide` и native app-state listener к тому же менеджеру сессии. Запись при уходе в фон корректно завершается/отменяется с явным состоянием; интерфейс не должен задним числом переключиться в предпросмотр уже закрытой сессии. При возврате не запрашивать камеру автоматически.
12. Применить согласованный профиль ограничений камеры и fallback. Выбор VP9 первым в `proofPickVideoMime` пересмотреть по измерению: `isTypeSupported` означает поддержку формата, но не гарантирует плавное кодирование. Выбрать поддерживаемый и измеренно приемлемый вариант; native capture не вводить без отдельного доказанного выигрыша и проверки iOS/Android.

## Границы

- Не изменять серверные правила выполнения, лимиты пропусков, битов, депозитов, штрафов или ручной проверки пруфов.
- Не упрощать рисунок персонажа, не менять сцены, цвета или тексты продукта вне необходимых состояний камеры.
- Не добавлять React, новую библиотеку анимации, WebGL или новую нативную камеру как обязательное условие оптимизации.
- Не давать фоновой камере продолжать запись ради «бесшовности» и не менять разрешения телефона без действия пользователя.
- Не называть рост памяти доказанной утечкой, пока нет воспроизводимого прогона с освобождением ресурсов.
- При несовпадении указанных функций с кодом обновить привязки после чтения, а не переносить решение вслепую из устаревшего графа.

## Проверка

- **Mechanical**: `node --check frontend/script.js`, `node --check frontend/path-journey.js`, `node --check frontend/path-traveler.js`, `npm test`, `node scripts/check-release.mjs`. Подписанная APK и AAB собираются; ресурсы APK сверяются с исходниками; ключи остаются вне Git.
- **Сцены**: 20 циклов Today→Marathon→Today с 1/6/20 маршрутами. Для неизменённой карточки идентичность DOM-узла и gradient ID сохраняются; герой не телепортируется и не повторяет шаг; количество scene instance стабилизируется после первого обхода.
- **Студия**: первый и 20-й вход при 5 вариантах экипировки и 6 сценах. Повторный вход не создаёт artwork заново. На A22 целевой p95 выполнения JS в обработчике повторного входа ≤50 мс, отсутствие отдельной задачи >50 мс после оптимизации; отображение выбранного предмета начинается в пределах 100 мс от тапа при прогретом экране. Измерять trace, а не временем вызова ADB.
- **Медиа**: 20 циклов открытия/снимка/предпросмотра/пересъёмки/закрытия, 5 записей по 15 секунд, отказ камеры/микрофона, сворачивание и блокировка. После выхода все принадлежащие сессии tracks имеют `readyState === 'ended'`, callbacks не выполняются, `proofChunks` пуст, `srcObject` очищен, нет активных object URL прежней сессии.
- **Память**: в контролируемом повторяемом прогоне сохранять PSS и heap до/после каждого цикла. После прогрева и GC не должно быть монотонного накопления старых tracks, canvas, Blob и video DOM. Точный допуск MiB задаётся по baseline устройства; не сравнивать разные процессы/сессии как одну кривую.
- **Feel check**: проверить шаг в обычной скорости и при 10% playback, смену экипировки, быстрый возврат между экранами, `prefers-reduced-motion`. Кнопки остаются доступными во время наградного шага; камера не должна замедлять закрытие окна; повторный вход не запускает уже завершённую анимацию.
- **Done when**: сцены сохраняются между экранами, studio updates становятся выборочными, жизненный цикл камеры проверен на устройстве, а измерения до/после приложены к отчёту с одинаковым сценарием. Одного успешного unit test для завершения плана недостаточно.
