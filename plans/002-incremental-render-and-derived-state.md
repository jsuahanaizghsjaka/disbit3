## Целевой результат

1. Нажатие обновляет только затронутую карточку, общие показатели видимого экрана и зависимый марафон. Скрытые экраны получают признак устаревания; их DOM пересчитывается при открытии.
2. Повторный вход в уже подготовленную вкладку без изменения данных использует существующие узлы и показатели.
3. Сеть подтверждает выполнение и финансовые результаты. Мгновенный визуальный отклик означает «действие принято / идёт проверка», пока сервер не ответил.
4. Представление одной карточки не уничтожает фокус, раскрытые детали, позицию прокрутки и состояние pending другой карточки.
5. Цели проекта после выполнения зависимых исправлений: синхронная работа прогретого переключения вкладки ≤20 мс на наборе 30 обещаний / 365 дней при CPU×1; видимый отклик на ввод ≤50 мс; p95 локального перехода до первого содержательного кадра ≤150 мс. Это критерии приёмки, а не уже достигнутые показатели.
6. На главном экране при отметке не вызываются скрытые `renderStats()`, `renderCalendar()`, `renderProfile()`; при посещении профиля не строится скрытый календарь.

## Соглашения проекта

- Бизнес-состояние остаётся в `frontend/script.js`; модули `path-*` дополняют представление.
- Изоляция аккаунтов и проверки владельца обязательны. При смене владельца очищаются все кеши вычислений и признаки готовности DOM.
- Пример устойчивого DOM: `renderWalkerCard()` в `frontend/script.js:1489–1494` проверяет stale-состояние до замены сцены. Аналогичный подход применить к карточкам и разделам, не копируя сложную логику SVG.
- Экранная навигация остаётся через `switchScreen()` и hash. Сохранить `pathScroll`, `aria-current`, фокус и ранний возврат при выборе текущего экрана (`frontend/script.js:3753–3785`).
- Не добавлять анимацию, чтобы скрыть вычислительную задержку. Высокочастотные вкладки должны отвечать сразу; параметры движения задаются отдельным планом.

## Шаги реализации

### 1. Зафиксировать воспроизводимую базу

1. Сохранить отдельный тестовый сценарий с тремя наборами из таблицы; все данные искусственные, реальные токены и production-данные не используются.
2. Измерять отдельно время обработчика, вычисляемых показателей, DOM-изменений и первый кадр после действия. Использовать `performance.mark/measure`, PerformanceObserver для long tasks и браузерный Performance trace.
3. Для каждого сценария выполнить один прогрев и не менее 20 повторов; сохранять медиану, p95, число узлов, число вызовов renderer и размер набора.
4. Не использовать `requestAnimationFrame` как доказательство того, что браузер уже показал кадр: связывать браузерный trace с визуальной записью и проверкой на устройстве.

### 2. Ввести явные причины изменения и версии данных

1. В `frontend/script.js` завести версии доменов: `habits`, `history`, `ledger`, `goals`, `profile`, `friends`, `settings` и текущего дня. Версия изменяется в точке фактической мутации, а не внутри renderer.
2. Ввести один интерфейс пометки областей как устаревших и один координатор обновления. Например: `invalidateUI({ habitIds, domains, screens })` и `flushVisibleUI()`; названия должны быть едиными во всех модулях.
3. Составить и пройти список всех мест вызова `render()` и мутаций. Не заменять все вызовы одной отложенной функцией вслепую: некоторые обработчики затем читают новый DOM или возвращают фокус. Для таких мест предусмотреть явный синхронный flush только нужной области.
4. Хранить готовность/версию каждого экрана и каждой карточки. `switchScreen()` показывает экран, обновляет его только при устаревании и сохраняет прежний scroll/focus-контракт.

Матрица обязательной инвалидизации:

| Изменение | Немедленно на видимом экране | Отложенно до открытия |
|---|---|---|
| Сегодняшняя отметка / минимум / грэйс-день | Карточка обещания, неделя, итог дня, связанный марафон | Статистика, календарь, достижения, профиль |
| Название / иконка / цвет | Изменённая карточка и открытые её детали | Подписи связанных экранов |
| Расписание / цель / архив | Карточка, счётчики дня, открытые детали, связанный марафон | Календарь, статистика, профиль |
| Изменение марафона / экипировки | Открытая сцена и её подписи | Неоткрытые сцены / магазин |
| Полученные операции | Видимые баланс и история | Скрытые подробности; графики штрафов |
| Смена аккаунта, импорт, смена дня/часового пояса | Сброс кешей, затем первый видимый экран | Остальные разделы строятся при открытии |

### 3. Получать производные показатели один раз на версию данных

1. Вынести чистый слой расчётов: показатели по обещанию, по дню, по неделе, по марафону и по набору. Источники истины — существующие функции `doneOn`, `isScheduledOn`, `isRequiredOn`, правила архива и пропусков.
2. Кеш серии хранить по `habit.id` и версии истории/расписания этого обещания, текущему дню и часовому поясу. Переименование/цвет не должны пересчитывать историю. Смена дня, импорт и применение удалённого состояния инвалидируют соответствующие записи.
3. Одна изменившаяся отметка должна вызывать максимум один расчёт текущей и лучшей серии данного обещания на новую версию, даже если результат нужен сразу нескольким областям.
4. Для календаря и heatmap один раз вычислять запись даты: запланировано, выполнено, минимум, пропуски, штрафной статус. Визуальное и текстовое представления читают один результат.
5. Не кешировать DOM-зависимые значения в бизнес-слое. Не менять трактовку гибких недель, грэйс-дней, минимумов, архива, прошлых дней и серверных штрафов.

### 4. Сохранить узлы карточек и обновлять их по ключам

1. Перевести `renderHabits()` с очистки трёх списков на обновление по `habit.id`. Создавать карточку только для нового обещания; удалять только исчезнувшую; перемещать только при изменении группы/порядка.
2. Назначить делегированные обработчики один раз на устойчивый контейнер. Сохранить защиту от повторного нажатия `pendingHabitMarks`, сообщения ошибок и подтверждение отмены/удаления.
3. Обновлять текст/классы/атрибуты конкретных полей, если значение изменилось. Не заменять всю карточку при смене pending или одной цифры.
4. После ответа сервера применить подтверждённое состояние, инвалидировать связанные показатели, обновить видимые области. При ошибке убрать pending и показать доступный повтор без фиктивного выполнения.
5. Сохранить закрепление и перемещение между «Сегодня»/«Выходные». Состояние фокуса и клавиатурного управления должно переживать изменение одного обещания.

### 5. Сделать статистику и подробности ленивыми

1. `renderStats()` запускать при первом открытии статистики и при изменении её версии. Скрытая статистика не строится от нажатия в Today.
2. Создать 112 узлов heatmap один раз для выбранного диапазона, затем менять классы/подписи. При изменении диапазона перестроить нужный диапазон.
3. Текстовую историю и длинные списки внутри закрытых `details` строить при первом раскрытии; при изменении версии перестраивать при следующем раскрытии. Сохранять доступное текстовое представление данных.
4. Календарь обновлять при изменении месяца или его зависимых данных, а не при любой правке профиля.
5. Для 100 обещаний с трёхлетней историей проверить холодное открытие статистики. Если остаётся задача >50 мс, делить подготовку на отменяемые порции и показывать честное состояние подготовки; не строить скрытые порции после ухода со статистики.

### 6. Убрать повторное представление друзей и профиля

1. Владелец сетевого ответа и кеша друзей определяется планом 003; здесь обеспечить один вызов соответствующего обновления на новую версию данных.
2. `renderProfile()` не должен повторно строить все дочерние разделы, если изменилась только одна область. Разделить идентичность, депозит, награды, достижения и архив по версиям.
3. Проверить, что обновление данных друзей не закрывает раскрытое совместное обещание и не перемещает фокус.

## Границы

- Не менять серверные маршруты, правила выполнения, финансовые правила, количество пропусков и цену битов.
- Не делать оптимистическое окончательное выполнение, зачисление, списание или покупку до ответа сервера.
- Не переносить проект на React/React Native и не добавлять новую библиотеку состояния ради этого плана.
- Не удалять текущие защиты повторных действий, аккаунтные ключи, правила отмены и focus trap.
- Не трогать пользовательские удаления старых `server-backups/`.
- Если исходные функции отличаются от коммита `e9d98b5`, сначала уточнить актуальную карту вызовов и обновить план; не переносить номера строк механически.
