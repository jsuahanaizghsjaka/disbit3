# 007 — Ускорить запуск и повторную загрузку веб-ресурсов

- **Status**: TODO
- **Commit**: `e9d98b5`
- **Severity**: MEDIUM; повышение до HIGH только при подтверждённом превышении бюджета запуска
- **Category**: Performance, Cohesion & tokens
- **Estimated scope**: `frontend/index.html`, `frontend/script.js`, `frontend/fonts.css`, `backend/server.js`, конфигурация упаковки/CI при доказанной необходимости. Ориентир: 4–8 файлов; настройка HTTP и реорганизация загрузки — отдельные подэтапы.
- **Зависимости**: сначала планы 001–002 с устранением дорогого форматирования/лишних вычислений и планом выборочной отрисовки. Разделение JS на chunks выполняется после повторного измерения этих изменений; новый framework не требуется.

## Проблема

### Веб-ресурсы каждый раз проходят перепроверку кэша

На рабочем сайте проверены HEAD-ответы `/`, `/script.js`, `/style.css`, `/fonts/onest-cyrillic.woff2`: у всех был `Cache-Control: public, max-age=0`, ETag и Last-Modified. Это позволяет 304, но оставляет сетевой round trip при повторном открытии. Имена файлов стабильны между релизами.

```js
// backend/server.js:75–76 — current
// раздаём фронтенд статикой (http://localhost:3000 → приложение)
app.use(express.static(path.join(__dirname, '..', 'frontend')));
```

Сжатие уже есть: для рабочего `script.js` подтверждён `gzip`. Локальный gzip того же исходника дал 79 805 Б при исходных 278 196 Б; локальный размер gzip не следует выдавать за точный объём каждого сетевого ответа. Задача не состоит в повторном «включении сжатия».

### Весь интерфейс загружается до готовности первого экрана

```html
<!-- frontend/index.html:11–17 — current -->
<link rel="stylesheet" href="fonts.css" />
<link rel="stylesheet" href="style.css" />
<link rel="stylesheet" href="path-ui.css" />
<link rel="stylesheet" href="path-journey.css" />
<link rel="stylesheet" href="path-insights.css" />
<link rel="stylesheet" href="path-support.css" />
<link rel="stylesheet" href="path-motion.css" />

<!-- frontend/index.html:1403–1412 — current -->
<script src="vendor/qrcode.js"></script>
<script src="path-traveler.js"></script>
<script src="path-journey.js"></script>
<script src="path-insights.js"></script>
<script src="path-support.js"></script>
<script src="path-ui.js"></script>
<script src="path-motion.js"></script>
<script src="path-faces.js"></script>
<script src="path-archive.js"></script>
<script src="script.js"></script>
```

В сумме основные JS-файлы занимают 394 333 Б без gzip, CSS — 180 424 Б, `index.html` — 89 331 Б. Это исходные размеры, а не доказанная причина всех задержек. В частности, большая часть файлов подключена в конце body: проблема не формулируется как «все скрипты блокируют получение начала HTML».

Файлы пользуются общими глобальными функциями. Простая перестановка тегов или добавление `async` может вызвать недетерминированную ошибку запуска. Не выполнять такое изменение как «быстрый фикс».

### Сплэш скрывается после синхронного общего init

```js
// frontend/script.js:5136–5150 — current (сокращённый фрагмент)
function init() {
  wirePathUI();
  wireJourneyUI();
  wireInsightsUI();
  wireSupportUI();
  wireMotionUI();
  applyTheme();
  // ...
  buildPickers();
  buildDayPicker();
```

```js
// frontend/script.js:5388–5409 — current (фрагменты)
switchScreen(location.hash.slice(1) || 'today', false);
const fresh = settlePastDays();
render();
// ... показ интро/входа/итогов ...
wireNativeShell();
apiBootstrap();

// frontend/script.js:4933–4935 — current
// Сплэш держится до этого момента (launchAutoHide выключен в конфиге):
// прячем его, только когда экран уже отрисован, иначе видна белая вспышка.
nativePlugin('SplashScreen')?.hide()?.catch?.(() => {});
```

Блокирующий начальный `render()` рисует несколько экранов и статистику; его оптимизация входит в предыдущие планы. Здесь требуется явно отличить готовность Android Activity от готовности веб-интерфейса и отделить обязательный старт от необязательной подготовки скрытых экранов.

Baseline на Galaxy A22 / Android 13 / WebView 155 / установленной 1.0.6: три холодных `am start -W` дали `TotalTime` 1066/1013/967 мс. Эти значения **не являются web-ready**, временем до работающих кнопок, LCP или INP. Прогон навигации из 12 тапов дал `gfxinfo` p95 кадра 81/48/73 мс в трёх прогонах; это не точный FPS и не измерение задержки конкретного тапа. Замеры в таком виде сохраняются только как исходный сигнал, после изменений нужен одинаковый подробный trace.

## Целевой результат

1. У запуска есть отдельные отметки: `app:bootstrap:start`, `app:first-screen:mounted`, `app:first-screen:painted`, `app:interactive`, `app:server-state:ready`. Последняя отметка не задерживает базовую навигацию при доступном безопасном локальном состоянии; денежные подтверждения по-прежнему требуют сервера.
2. Целевой бюджет на A22 после прогрева: обратная связь на тап ≤100 мс, готовая смена обычной вкладки p95 ≤150 мс, отсутствие JS-задачи >50 мс, относящейся к повторной загрузке необязательного модуля. Нативный cold start и web-ready измеряются раздельно. Первую численную цель web-ready установить по корректному baseline, затем требовать улучшение минимум на 30% на одинаковом сценарии без сетевой зависимости.
3. Статический ресурс с fingerprint получает `Cache-Control: public, max-age=31536000, immutable`. HTML/manifest без fingerprint — `no-cache` с валидатором либо `max-age=0, must-revalidate`. Приватные API и пользовательские медиа этим правилом не охватываются.
4. При повторной загрузке веб-версии в пределах года неизменённые fingerprinted JS/CSS/шрифты читаются из локального HTTP-кэша без запроса к origin. Новый релиз получает новый fingerprint, а HTML не залипает на старой ссылке.
5. Для APK ресурсы остаются локальными. HTTP-кэш не считается ускорением переходов APK. Любое изменение `webDir`/пакетирования проверяется на Android и iOS CI отдельно.
6. Существующая палитра, Glass Light dock, набор функций, автономные локальные ресурсы и серверная изоляция аккаунтов сохраняются.

## Соглашения проекта

- В `frontend/fonts.css:4–19` Onest уже локальный, имеет `font-display: swap` и unicode-range. Сохранить эти свойства. Не добавлять загрузку Google Fonts с внешнего домена.
- Текущая схема релизов использует отдельные каталоги `/srv/disbit/releases/<sha>` и атомарное переключение `current`; fingerprint и rollback должны работать вместе с ней.
- `capacitor.config.json:4` задаёт `webDir: "frontend"`; все нужные офлайн-ресурсы должны попасть в APK после `cap copy/sync`.
- QR создаётся только при соответствующем действии. Это хороший кандидат для отложенной подготовки, но нельзя удалять QR как функцию или менять формат приглашений.
- Существующие scripts/check-release.mjs и тесты hosted mode должны продолжать обнаруживать устаревший API URL, утечку секретов и неверную упаковку.

## Подшаги реализации

### A. Корректный baseline до изменения загрузки

1. Сохранить JSON отчёт для 10 холодных и 20 тёплых запусков A22 с одинаковым количеством привычек/маршрутов, WebView и режимом питания. Сохранять версию APK, Android, WebView, температуру/заряд и подключение зарядки. Не смешивать разные устройства и throttle DevTools с реальными данными.
2. Добавить только диагностические performance marks, не содержащие логина, привычек, платёжных данных или токена. `app:interactive` ставится после готовности обработчиков первого экрана и безопасного состояния формы; `app:first-screen:painted` — после двух rAF от окончания критической отрисовки. Android `TotalTime` держать отдельной колонкой.
3. Получить trace JS/style/layout/paint, long tasks и покрытие JS/CSS на сценариях запуска, Today↔Profile, Marathon↔Today и первого/повторного открытия студии. Кэш сетевых запросов, native bundle и время ответа API измерять отдельно.

### B. Версионирование и HTTP-кэш

4. Спроектировать воспроизводимую карту ресурсов релиза: fingerprint вычисляется из содержимого файла. Например, `script.<hash>.js`, `style.<hash>.css`, `onest-cyrillic.<hash>.woff2`; ссылки HTML и CSS URL переписываются одной командой упаковки. Не делать вручную случайные версии в отдельных тегах.
5. Разделить исходники и output релиза. Выбрать минимальную упаковку без смены framework: детерминированный скрипт/уже доступный инструмент. Новая библиотека анимации не нужна. Если будет выбран внешний build tool, закрепить версию и lockfile; обосновать его именно воспроизводимым fingerprint/minify, а не переписыванием продукта.
6. В `backend/server.js` задать `setHeaders`/отдельный static handler: immutable только для файлов, fingerprint которых проверяемо входит в имя и манифест сборки. HTML — revalidate; `/api/*`, приватные ответы и пруфы — без общего публичного кэша. Не применять `immutable` ко всем `.js` по расширению при стабильных именах.
7. Сохранить gzip на Caddy, проверить `Content-Encoding`, `Vary`, 200/304 и фактические размеры curl. Не включать второе сжатие того же ответа в Express. Проверить хотя бы gzip и несжатый клиент; шрифты WOFF2 не сжимать повторно принудительно.
8. Проверить переключение релиза A→B и откат B→A с уже открытой вкладкой. Если chunks грузятся по клику, старый HTML должен иметь доступ к собственным старым fingerprinted файлам в течение срока поддержки открытой вкладки; предусмотреть общий immutable asset каталог/сохранение ресурсов прошлых релизов. Просто хранить старый каталог вне Caddy-root недостаточно.

### C. Критический запуск и отложенная подготовка

9. После предыдущих планов повторить trace. Если init/parse всё ещё превышают бюджет, выделить критический этап: тема, insets, модель состояния/авторизации, навигация, первый экран, обязательный auth/onboarding gate. Перед скрытием splash должен существовать корректный видимый экран с доступными основными действиями, а не пустая подложка.
10. Подготовку скрытых пикеров, QR-библиотеки, магазина аватаров, редкой статистики и второстепенных overlay перенести на первое использование или спокойный idle-период после первого кадра. Каждый модуль имеет один promise готовности и одну инициализацию обработчиков. При двух быстрых входах создаётся один запрос/один набор DOM и listeners.
11. Не добавлять `async` существующим глобальным скриптам. При необходимости реального split сначала задать явный контракт зависимостей и `ensureFeatureReady(feature)`. Экран показывает доступную оболочку/индикатор загрузки без блокировки dock; быстрый выход отменяет обновление неактивного представления. Нельзя скрыть сетевой сбой загрузки chunks пустым экраном.
12. Не дробить CSS без проверки каскада: `style.css` → `path-ui.css` → `path-journey.css` → `path-insights.css` → `path-support.css` → `path-motion.css` сейчас содержит переопределения. Сначала установить эффективные токены/правила, затем отделять компоненты, сохраняя их порядок и computed styles. Удаление «мёртвых» правил — по CSS coverage плюс чтению условий, а не только по одному открытому экрану.
13. Проверить фактическое использование Unbounded. Если шрифт не нужен первому экрану, не preload его. При измеренном CLS/позднем появлении Onest preload только действительно критический subset с `as="font" type="font/woff2" crossorigin`, с hashed URL после упаковки. Не preload все четыре файла ради количества.
14. Если итоговые raw/transfer/parse бюджеты всё ещё не выполнены, добавить детерминированную минификацию с sourcemap для диагностики. Не обещать ускорение в разы по размеру исходного файла: новый результат сравнивается по parse/init/paint и работе кнопок на устройстве.

## Границы

- Не менять контракты API, бизнес-правила, серверный учёт денег, авторизацию и изоляцию аккаунтов ради ускорения.
- Не показывать устаревший финансовый остаток как подтверждённый, не откладывать проверку обязательных условий выполнения после фиктивного «успеха».
- Не внедрять React/React Native/новый framework или библиотеку анимации как обязательное условие плана.
- Не добавлять Service Worker для кэширования приватных API в этот этап. Его обновление, офлайн-запись, конфликты и очистка аккаунта требуют отдельного проекта.
- Не сокращать splash таймером без готового видимого UI и не считать `am start -W TotalTime` временем до работающего интерфейса.
- Не включать immutable для ресурсов без fingerprint, HTML или персональных данных.
- Не трогать секреты/keystore, каталоги пользовательских данных, старые бэкапы и конфигурацию соседних сайтов. Deploy выполняется после staging, с предусмотренным откатом.

## Проверка

- **Mechanical**: `npm test`, `node scripts/check-release.mjs`, проверки JS синтаксиса; сборка Android APK/AAB и iOS simulator в CI. Извлечённые web assets APK совпадают с выходом упаковки. Первый запуск APK без внешней загрузки скриптов должен открыть локальную оболочку.
- **HTTP**: curl для HTML/manifest/hashed JS/hashed CSS/WOFF2/API. Проверить exact Cache-Control по типам; отсутствие публичного кэша для приватных ответов; gzip и Vary; новая версия меняет hash только изменившегося содержимого. Повторное открытие в браузере не запрашивает неизменённые immutable файлы у origin.
- **Release cycle**: загрузить A, открыть редкую функцию, выпустить B, вернуться в старую вкладку и открыть ранее не загруженную функцию; проверить работоспособность и отсутствие 404. Повторить rollback. Не тестировать этот сценарий заменой рабочей базы.
- **Runtime**: desktop 1280 px и mobile 360 px, гостевой/авторизованный синтетический аккаунт, интро, auth, прямой hash на редкий экран, медленная сеть, сетевой отказ при lazy module. Нет ReferenceError, дублирующихся listeners, длинной пустой области и горизонтального overflow.
- **Device**: A22 Android 13/WebView 155 и хотя бы один Android 15/16 плюс iPhone/WebKit перед релизом. Сравнить распределения web-ready, first paint, tab paint и long tasks до/после. Прогон `gfxinfo` не выдавать за web FPS/INP; использовать его вместе с trace и событиями приложения.
- **Feel check**: после тапа dock сразу подтверждает выбранный раздел; появление новых данных не сдвигает весь экран; обычная навигация не ждёт QR, камеры или магазина; при быстрых входах/выходах не вспыхивает неактивный экран. `prefers-reduced-motion` продолжает работать и не влияет на готовность обработчиков.
- **Done when**: утверждённые бюджеты достигнуты по повторяемым измерениям, fingerprint/cache переживают выпуск и откат, native APK не зависит от HTTP-кэша для ресурсов, а отчёт показывает отдельно сетевое, JS и визуальное улучшение. Сам по себе меньший ZIP или успешная минификация не закрывают план.
