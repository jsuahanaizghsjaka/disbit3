## Проблема

Сейчас нет общего измерения «касание → первый видимый ответ → готовность раздела». Один системный показатель `gfxinfo` не объясняет, сколько заняли JavaScript, GPU, сеть и клавиатура. Добавление красивого перехода может скрыть задержку, не сократив её.

Контрольные исходники: `frontend/script.js:3753–3785` (`switchScreen`), `:3796–3798` (`openSheet`), `frontend/path-support.js:44–50` (`apiBootstrap`), `frontend/path-motion.js:209–254` (wheel). Сравнивать с кодом `e9d98b5`, а не с устаревшими номерами функций из графа.

## Измерения и точные цели проекта

Цели ниже — условия приёмки, не уже достигнутые результаты:

| Сценарий | Цель |
|---|---|
| Первое визуальное состояние обычной кнопки | p95 ≤50 мс на A22, не дожидаясь сети |
| Тёплый переход вкладки, данные уже загружены | касание → первый кадр целевого раздела p95 ≤150 мс |
| Синхронный обработчик тёплой вкладки | p95 ≤20 мс на наборе 30 обещаний / 365 дней |
| Работа JS в кадре активного жеста | p95 ≤8 мс; нет повторного создания строк wheel |
| Обычное изменение отметки | нет долгой задачи >50 мс, вызванной невидимой статистикой |
| Стабильность кадров | промежуточная цель p95 кадра ≤33 мс в режиме 60 Гц; финальная — большинство кадров в бюджете 16,7 мс |
| Системные пропуски сроков кадров | снизить минимум на 50% относительно повторно снятой контролируемой базы, без ухудшения корректности |
| Веб, реальные сессии | INP ≤200 мс, LCP ≤2,5 с, CLS ≤0,1 на p75 отдельно для mobile/desktop |

60 Гц — 16,7 мс на кадр, 90 Гц — 11,1 мс; частоту дисплея фиксировать в отчёте. Не превращать системный `Janky frames` в «FPS», а длительность `am start -W` — в готовность аккаунта. Порог Core Web Vitals относится к полевым сессиям, а не к единственному лабораторному нажатию.

## Подшаги

1. Добавить выключенный по умолчанию диагностический режим: `performance.mark/measure` для nav-start, shell-ready, first-target-frame, data-ready, save-start/save-confirmed, proof-camera-ready.
2. Регистрировать длительные задачи через `PerformanceObserver` и Event Timing, если API поддерживается. При отсутствии API показывать «недоступно», не ноль. Для настоящего INP использовать проверенную реализацию web-vitals; не называть простой замер двух rAF официальным INP.
3. Хранить только действие, длительность, версию, тип платформы и размер тестового набора. Не собирать имена обещаний, почту, Bearer-токены, фото, суммы личных операций или содержимое поля.
4. В режиме разработчика счётчики должны показывать вызовы render-функций, создание/удаление карточек, запросы in-flight и число активных media tracks. Диагностика не должна постоянно нагружать production.
5. Подготовить независимые наборы: пустой аккаунт; 5/90/1, 30/365/6 и 100/1095/20 (обещаний/дней/маршрутов). Стресс-набор не считать типичным пользователем.
6. На каждый сценарий: один прогрев, затем минимум 20 повторов. Сохранять медиану и p95, версию OS/WebView/браузера, частоту, заряд/питание, температуру и сеть. Нынешние три прогона — только исходный ориентир.
7. Не запускать тяжёлый браузерный CPU-бенчмарк одновременно с контрольной записью трассы A22. Давать устройству остыть между длинными сериями.
8. Для GPU/layout снять Perfetto или Android Studio System Trace: отдельно frame timeline, UI thread, RenderThread, WebView renderer. JS-профиль с debug WebView выполнять только в отдельной QA-сборке; remote debugging не включать постоянно в публичном release.
9. Повторить тесты под плохой сетью: 150/300 мс RTT, offline, потеря соединения во время запроса, возврат приложения из фона. Проверять внешний вид сохранённых данных и таймаут, не только время ответа.
10. Сопоставить результаты до/после каждого этапа. При ухудшении p95 более чем на 10% вернуть изменение или объяснить в отчёте отдельным принятым компромиссом.

## Выпуск

1. Запустить соответствующие контрактные тесты проекта: `npm test`, синтаксическую проверку изменённых JS и существующий релизный gate `node scripts/check-release.mjs`.
2. Приложить браузерные тесты только на синтетических данных; существующий `tests/browser-wallet-history.js` остаётся проверкой изоляции истории, а не тестом всей производительности.
3. Собрать подписанные APK/AAB с новым versionCode; проверить сертификат и точное совпадение веб-ресурсов в APK с принятой версией кода.
4. Проверить staging, резервную копию и возможность отката перед production; не включать live payments из-за успешных performance-тестов.
5. Выпускать по небольшим изменениям: форматтер → выборочный render → модели → синхронизация → жесты → медиа/ресурсы. Новый декоративный переход вкладок — последним и только при сохранении бюджета.
6. Закрыть этап после отчёта с фактическими цифрами, скриншотами и конкретным перечнем оставшихся платформенных ограничений.
